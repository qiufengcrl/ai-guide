# 项目群聊

官方群聊容量：**2～6 个 Bot**（你算在成员里，加上 5 个岗位就是图上的「+3」那种编制）。

当前界面**没有群置顶、没有话题**。能改的只有：

| 栏 | 放什么 |
|----|--------|
| **名称** | 群的用途，例如 `交付：ai-guide`。不要写成成员名单。 |
| **描述** | 长期规则（下面「描述栏」整段）。官方：描述管「一直成立的规矩」，对话管「这一次任务」。 |
| **群里第一条消息** | 开工词 + 当前需求。 |

侧栏可以把这个群 **Pin** 到顶部，那是钉会话，不是钉规则。

- 最小交付组：项目经理、开发、测试、评审。
- 已加调研时：勾选这 **5** 个（仍可再加发布，总数 ≤ 6）。

## 建群

1. 侧栏 New → 勾选本群实际编制（有调研就 5 个）。
2. **名称**改成「交付：<产品或仓库短名>」。若现在是「秋、测试、调研、评审、开发、项目经理」，改掉——那是自动拼的成员列表，不是群名。
3. **描述**贴下面「描述栏」整段。
4. 进群后把「开工词」作为**第一条消息**发出去（描述不会自动当指令跑）。
5. 之后你只派新活、拍板合入；日常交接让他们 `@` 彼此。

## 描述栏（贴进「这个群组的用途」）

群描述只用下面这 6 条，不要改成短版。这是编制规矩，**不是**项目介绍。仓库地址和当前任务写在群里第一条消息。

```
1. 所有权：项目经理维护任务表；调研交事实包；开发写；测试验；评审找阻断；我合入。调研不指派任务。改仓库时开发派 Cursor Cloud Agent，Grok Bot 电脑里不写产品代码。
2. 节奏：有实质进展再发言；不要每人一段日报。
3. 何时 @我：需要合入、发外、密钥、生产、范围变更、或两个岗位结论冲突。调研发现安全/合规阻断时也要 @我。
4. 何时不要 @我：常规交接、要源链接、要截图补证据。
5. 文件：共享电脑上 /workspace/handoff/<项目>/ 由项目经理建目录；调研写 research/，开发写 impl/，测试写 qa/，评审写 review/。禁止两人同时改同一文件。
6. 编制：不加第 7 个 Bot。缺能力先复用现有岗位，或 Duplicate 后再改范围。
```

没有调研时，删掉第 1、3 条里的调研句即可。第 1 条里「派 Cloud Agent」可保留。

## 开工词（发到群里，不是填进描述）

```
规则见本群描述。
@项目经理 根据我下一条消息拆成任务表：编号、owner、完成定义、是否阻塞。需求不清或要对照来源时先 @调研，不要自己写代码或测。
```

下一条换成真实需求，例如：「把登录失败提示改成可访问的文案，并补回归」。

没有调研的 4 人群：把「先 @调研」改成「不要自己写代码或测」。

## 站会（可选，由项目经理一条例程收集）

每个工作日，项目经理在群里贴一张表：完成 / 阻塞 / 需要人。调研一栏只填「事实包是否齐 / 卡在哪个来源」。

- 其他 Bot **不要**各自再开例程报站会。
- 站会 **不得**自动派新活。新活只由你说。
